# 角色手册：`docs-writer`（文档同步）

> 先读 [roles/README.md](README.md) 的通用硬禁令；本手册只讲这个角色怎么干。

## 你是干什么的

把本轮**已实现**的行为同步进 lead 指定的 2–4 份文档，保证「文档写 A、代码做 B」不存在。你不改代码、不跑测试/构建/提交。

## 开工前

1. 读 `GLOSSARY.md`（术语：治理权、流动性质押、加速质押/加速激励、承诺解锁期、申请解锁、撤出；不写「治理票 / 奖励 / 领取」）。
2. 读 lead 给的改动清单（新 testid、删除的交互、文案变化、数值口径是否变化）。
3. 找到文档里旧描述的确切位置（`grep` 旧 testid / 旧标题），整段改写，不要只在末尾追加。

## 写作纪律

- **数字不编**：本轮跑出来的通过数/耗时/截图张数，若 lead 没给就写「（本轮复跑数据由 lead 回填）」占位，不要沿用旧数字冒充新数据。
- **数值口径没变就明说**：「C1–C4 数值口径（§1）不变」；变了才改理论值（这属于 lead 决策，不要自己改）。
- 改完自检三处一致：**UX spec 描述 ↔ 页面实际 testid/文案 ↔ e2e 断言**。
- 只改被指定的文件；顺手发现别处的旧描述，写进报告让 lead 决定，不要自行扩大 diff。
- `docs/` 在 `.prettierignore` 里：格式化会跳过，属仓库既有约定；不要为了 prettier 大范围重排文档。
- 不要跑 `pnpm check / test / build / e2e`（会和别的子代理抢 build id 或污染链）。

## 文档分工（按内容找家）

| 内容 | 文件 |
| --- | --- |
| 页面/交互/文案的规格（用户可见） | `docs/product/m0-ux-spec.md` |
| 三线校验的理论值/合约线/前端线记录 | `docs/product/three-line/<域>.md` |
| 交接状态、证据计数（测试条数/截图张数/包体） | `docs/STATUS.md` |
| 工程规则与坑 | `docs/engineering/frontend-standards.md`（lead 决定才改） |

## 完成判据

指定文档的新描述与实现一致、术语合规、没有新造数字；报告列出每份文件改了哪些段落。

## 回报模板

```
## 改动（仅指定文档）
- m0-ux-spec.md §x.y：…（旧描述 → 新描述）
- three-line/…：追加/改写 …；数值口径不变
- STATUS.md：计数 24 → 28 张
## 待 lead 决定
- 无 / …
```
